# 项目归档与恢复设计说明

## 背景

当前 TestOps 已支持项目创建、文档上传、用例生成与导入、评审发布、自动化计划与设置中心，但缺少项目生命周期管理中的“归档”能力。对于企业场景，这会带来两个问题：

1. 已停用项目仍长期混在活跃项目列表中，影响管理效率。
2. 用户没有安全的“移出主列表”方式，只能依赖物理删除，但物理删除风险过高，不适合作为默认操作。

本设计的目标是补齐企业后台常见的软删除级能力：项目归档与恢复。

## 目标

第一版实现以下能力：

1. 项目支持归档与恢复，不做物理删除。
2. 项目列表默认只展示活跃项目，可切换查看已归档项目。
3. 项目目录页和项目详情页都提供归档/恢复入口。
4. 已归档项目保留全部关联数据，但停止继续推进主业务流程。

## 非目标

本次不包含以下内容：

1. 物理删除项目。
2. 回收站、保留期、自动清理策略。
3. 基于角色的权限控制。
4. 删除审计人、归档操作人、操作日志体系。
5. 批量归档、批量恢复。

## 用户场景

### 场景 1：归档已完成项目

测试负责人在项目目录中看到某个项目已交付完成，不再需要继续上传资料、生成用例或创建计划。用户点击“归档项目”后，项目从默认项目列表移除，但关联文档、用例、评审和计划数据仍保留，后续可恢复查看。

### 场景 2：恢复误归档项目

用户切换到“已归档项目”视图，发现某个项目仍需补充测试内容。用户点击“恢复项目”后，该项目重新回到默认项目列表，并恢复活跃状态。

### 场景 3：查看已归档项目详情

用户进入已归档项目详情页，系统明确展示“项目已归档”的状态提示。用户仍可查看历史数据，但不能继续执行生成、导入、新建用例、创建计划等活跃操作，除非先恢复项目。

## 方案选择

本次采用“状态归档”方案，而不是前端本地隐藏或物理删除。

### 方案内容

1. 后端在 `projects.status` 中支持 `archived`。
2. 项目查询接口默认返回非归档项目。
3. 新增项目状态切换接口，支持活跃与归档间切换。
4. 前端在项目目录和项目详情页增加归档/恢复入口。

### 选择原因

1. 符合企业系统默认的安全策略。
2. 不破坏关联数据。
3. 后续若要扩展权限、审计、回收站，可沿用该状态模型继续演进。

## 数据模型设计

### 项目状态

沿用现有 `projects.status` 字段，增加：

- `active`：活跃项目
- `archived`：已归档项目

若当前库中默认状态不是 `active`，迁移中需统一映射到现有活跃值，并确保前后端展示层一致。

### 数据迁移

增加 Alembic migration：

1. 将 `projects.status` 的默认值设为活跃状态。
2. 确保已有项目状态被视为活跃项目。
3. 允许后续写入 `archived`。

本次不新增新表，不新增审计字段。

## 后端设计

### 接口调整

#### 1. 项目列表接口

现有：

- `GET /projects`
- `GET /project-summaries`

调整为支持查询参数：

- `status=active`
- `status=archived`
- `status=all`

默认值为 `active`。

#### 2. 项目状态更新接口

新增：

- `PATCH /projects/{project_id}/status`

请求体：

```json
{
  "status": "archived"
}
```

或：

```json
{
  "status": "active"
}
```

返回值为更新后的项目对象。

### 服务规则

#### 归档项目时

1. 保留项目及所有关联数据。
2. 不删除文档、用例、评审、计划、报告、环境、数据准备记录。
3. 项目从默认活跃列表移除。

#### 恢复项目时

1. 状态恢复为活跃。
2. 项目重新进入默认列表。
3. 恢复后可继续使用主业务流程。

### 归档项目访问约束

第一版建议在写操作服务侧增加保护，阻止对已归档项目继续发起活跃流程操作。最少覆盖：

1. 上传或新增文档
2. 生成用例
3. 导入用例
4. 在线新建用例
5. 创建自动化计划

接口返回建议使用 `409 Conflict`，文案统一为“项目已归档，请先恢复后再继续操作”。

只读查询可继续保留：

1. 查看项目详情
2. 查看文档列表
3. 查看测试用例列表
4. 查看评审记录
5. 查看自动化计划与设置数据

## 前端设计

### 1. 项目目录页

新增“项目视图切换”：

1. `进行中`
2. `已归档`

默认进入 `进行中`。

每张项目卡片增加“更多操作”入口：

1. 活跃项目显示“归档项目”
2. 已归档项目显示“恢复项目”

交互要求：

1. 归档前弹确认框，提示“归档后项目将从默认列表隐藏，但不会删除已有数据”。
2. 恢复前弹确认框，提示“恢复后项目将重新出现在默认列表，并可继续使用”。

### 2. 项目详情页

在项目标题区域增加状态操作入口：

1. 活跃项目显示“归档项目”
2. 已归档项目显示“恢复项目”

已归档项目展示明显状态横幅：

- “该项目已归档，可查看历史数据。如需继续操作，请先恢复项目。”

### 3. 已归档项目的操作限制

前端在归档状态下禁用以下主操作按钮：

1. 上传资料生成
2. 导入用例
3. 在线编写用例
4. 新建生成任务
5. 新建自动化计划

禁用时显示统一说明：

- “项目已归档，请先恢复后再继续操作”

### 4. 文案

新增或调整文案包括：

1. `归档项目`
2. `恢复项目`
3. `已归档`
4. `进行中`
5. `项目已归档，请先恢复后再继续操作`
6. `归档后项目将从默认列表隐藏，但不会删除已有数据`
7. `恢复后项目将重新出现在默认列表`

## 错误处理

### 归档失败

场景：

1. 项目不存在
2. 状态非法
3. 后端更新失败

处理：

1. 返回标准错误码和清晰中文提示
2. 前端保留当前列表状态，不做乐观更新回滚遗漏

### 已归档项目继续写操作

场景：

1. 用户停留在旧页面，项目被归档后仍尝试继续操作
2. 直接通过深链或接口调用发起写操作

处理：

1. 服务端统一拦截
2. 前端 toast 提示“项目已归档，请先恢复后再继续操作”

## 测试方案

### 后端

1. 项目状态迁移测试
2. 活跃/归档列表过滤测试
3. 项目归档接口测试
4. 项目恢复接口测试
5. 已归档项目写操作拦截测试

### 前端

1. 项目目录页视图切换测试
2. 归档/恢复按钮展示测试
3. 归档确认框与恢复确认框测试
4. 归档后项目从默认列表消失测试
5. 已归档项目详情页状态提示测试
6. 已归档项目主操作禁用测试

### 集成回归

1. 创建项目后归档，再恢复
2. 有文档、有用例、有计划的项目归档后数据仍可查看
3. 已归档项目不能继续生成、导入、新建
4. 恢复后主流程重新可用

## 风险与注意事项

1. 当前多个服务模块都通过 `_get_project` 或 `_get_project_or_404` 获取项目，归档限制不能只做前端，需要服务层统一保护。
2. 如果现有 `status` 文案与数据库值不完全一致，需要先统一映射规则，避免前后端判断分叉。
3. 项目汇总接口和项目列表接口都要支持过滤，否则目录页和其他引用处可能状态不一致。

## 分阶段落地建议

### Phase 1

1. 支持归档/恢复状态
2. 列表视图切换
3. 详情页状态横幅
4. 写操作禁用与服务端拦截

### Phase 2

1. 审计字段与操作记录
2. 权限控制
3. 批量归档/恢复
4. 永久删除或回收站机制

## 验收标准

满足以下条件即可视为完成：

1. 用户可在项目目录和项目详情中归档、恢复项目。
2. 默认项目列表不显示已归档项目。
3. 用户可切换查看已归档项目并恢复它们。
4. 已归档项目保留历史数据，但不能继续推进核心写操作。
5. 相关前后端测试通过，现有主流程未回归损坏。
